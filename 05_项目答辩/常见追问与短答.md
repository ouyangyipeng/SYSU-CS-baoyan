# 常见追问与短答

每题先回答老师问的部分，再给一个机制或证据。初次回答可练到约 20—30 秒；是否展开由问题深度决定，不把每个问题都变成一次完整项目汇报。

## 项目的七个基本问题

| 问题 | 回答要点 |
|---|---|
| 为什么做这个项目？ | 具体场景中现有方法的限制，说明它为什么值得解决 |
| 你负责了什么？ | 说出负责的模块或研究环节、亲自完成的产物，与队友分工 |
| 用了什么方法？ | 输入、关键处理步骤、输出，以及一处关键设计取舍 |
| 创新在哪里？ | 明确相对哪个基线，改了哪个机制，为什么不是已有方法直接应用 |
| 有什么结果？ | 在什么设备、数据和指标下，相比什么基线获得什么结果 |
| 最大困难是什么？ | 具体现象、原因定位、尝试与修复，避免只说时间紧或代码量大 |
| 有哪些不足？ | 已知限制、适用边界，以及下一步如何验证或改进 |

## 方法、结果和个人贡献的区别

方法回答“怎么做”；结果回答“做得怎样”；个人贡献回答“哪些是自己完成的”。不要把它们揉成一句“做了一个系统，效果很好”。

通用示例：在检索服务中加入缓存是方法；在同一查询集上减少响应延迟是结果；负责缓存策略、实现与实验是个人贡献。若不能确认测试数据，就不补造具体提升比例。

## 实验相关追问

**为什么选这个基线？** 说明它解决同类问题、代表什么常见做法，以及比较条件是否一致。不能只选明显较弱的方案。

**提升来自哪个部分？** 用消融或替换实验说明；没有做过消融，就说目前证据只能支持整体改进，尚不能精确归因。

**为什么可信？** 说明数据划分、重复次数、随机性控制、测量方法和正确性检查。最好值、均值与尾延迟是不同口径。

**局部性能变好，系统就更好吗？** 不一定。还要检查端到端延迟、资源消耗、吞吐和功能正确性。

**提高了多少倍？** 先说明比值方向。新吞吐除以旧吞吐是吞吐比；旧延迟除以新延迟是加速比。不要混淆百分比增幅和“变为几倍”。

## 专业术语与基础

- 每个写进 PPT 的术语至少能给出定义、作用和与项目的关系。
- 问算法细节时，说明状态或数据结构、处理步骤、复杂度。问系统细节时，说明模块接口、状态变化和正确性约束。
- 若对方把系统机制称为算法，可以自然澄清具体研究对象，然后回答实现细节。
- 问数学应用时，选择实际用到的概念，例如矩阵表示、相似度、图结构、均值方差或约束优化，不主动夸大理论深度。

## 介绍一篇读过的论文

按“问题—方法—结果—局限”介绍，补一句它与自己的工作有什么关系。题名、作者或年份记不准时可以说明；研究问题与关键机制应能解释。

论文阅读数量按实际情况回答，区分浏览摘要、通读、精读和复现。不能用大量浏览记录替代对一篇代表性论文的理解。

## 不确定时怎样回答

- 知道一部分：先说能确认的部分，再指出缺少的条件。
- 记不清数字：说明指标与趋势，不临时编一个数。
- 没做过实验：明确当前没有这项证据，可以说明准备怎样验证。
- 发现自己刚才说错：直接更正定义或条件，再继续回答。
